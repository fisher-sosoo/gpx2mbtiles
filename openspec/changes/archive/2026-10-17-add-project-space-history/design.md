# Design

## Context

现有 `task_manager` 已经用「SQLite 账本 + 目录」管理瓦片任务，项目空间复刻同一套模式，
不引入新依赖、不发明新范式。

## Goals / Non-Goals

**Goals:**

- 转换产物可持久化、可回看、可重转、可删。
- 有上限的磁盘占用，不会无限增长。

**Non-Goals:**

- 不做多用户/权限模型（个人自用，沿用 `AUTH_TOKEN` 单一凭据）。
- 不与瓦片任务合表（生命周期与清理策略不同）。

## Decisions

### D1 · 目录存文件，SQLite 存索引

历史列表要分页、排序、按时间倒序。扫目录 O(n) 且无法高效分页；
SQLite 一条 `ORDER BY created_at DESC LIMIT/OFFSET` 就够。

**替代方案**：纯文件系统 —— 否决，项目一多列表就慢，还得自己实现排序。

### D2 · 重转生成新项目而不是覆盖

用户改参数重转，往往想**对比**改动前后。覆盖会丢掉旧结果。
新项目用 `params.from_project` 记录来源，便于追溯。

### D3 · 保留原件

没有原件就无法重转。原件通常比产物小（KML 是文本），存下来代价很低。

### D4 · 淘汰用「条数 + 天数」双阈值

只按天数：用户猛转几十次时磁盘仍会涨。
只按条数：一个放半年的项目会被挤掉。
两者取「或」，任一超限就删。

### D5 · 保存失败不影响转换

项目落盘是「附加价值」，不能让它拖垮主流程。转换结果已经算出来了，
即使磁盘满也应该把 GPX 返回给用户。

## Risks / Trade-offs

- **[磁盘增长]** → 双阈值淘汰 + 单项目几十 KB 量级，200 个约数 MB。
- **[并发删除与读取交错]** → 先删账本再删目录；读取侧捕获文件缺失并明确报「已清理」。
- **[项目与瓦片任务割裂]** → 明确不在本项目做关联，需要时再引入。
