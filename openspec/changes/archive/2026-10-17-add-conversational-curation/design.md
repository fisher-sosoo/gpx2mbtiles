# Design

## Context

现在一次补点可能出 37 个地名点，用户往往只要十来个。此前只能全要或全不要。
方向 #3 要「多轮对话修正」，本轮聚焦**最需要修正的对象**：地名点。

## Goals / Non-Goals

**Goals:**

- 自然语言增删改地名点，且能承接上一轮。
- 模型不能随意改数据。

**Non-Goals:**

- 不做通用聊天机器人（不答与路线无关的问题）。
- 不做流式输出（单轮 2~4 秒，同步足够）。
- 不让模型修改轨迹坐标。

## Decisions

### D1 · 受限操作集，而不是自由改写

模型只输出四种操作：`drop_poi` / `keep_kinds` / `rename_poi` / `reset`。
服务端 `apply_ops` 逐条校验：名称必须存在于当前列表、类型必须真实存在、
新名字长度受限。越界一律进 `rejected`，数据不动。

**理由**：让模型直接返回「新列表」看似简单，但一旦它丢字段或编造坐标，
数据就被污染。受限操作把风险压到最小。

### D2 · 历史落 chat.json

每轮把最近 12 轮历史带进提示词，支持「再删掉刚才那两个」这类承接指代。
超过 60 条截断，避免无限增长。

### D3 · 首次修正前存快照

`pois.json` 增加 `original` 字段保存筛选前完整结果，`reset` 用它恢复。

### D4 · 深拷贝

实测发现：`list(items)` 只是浅拷贝，`rename_poi` 会直接改到调用方的 dict，
导致 `reset` 恢复出的是改过的数据。改为 `json` 深拷贝，并在测试里锁住。

## Risks / Trade-offs

- **[模型给出不存在的名字]** → 校验拦截并回报，用户能看到「未执行：没有叫 X 的地名点」。
- **[对话变长导致 token 增长]** → 只带最近 12 轮，且每条截断到 200 字。
- **[误删]** → 有 reset；且原始快照一直保留在 pois.json。
