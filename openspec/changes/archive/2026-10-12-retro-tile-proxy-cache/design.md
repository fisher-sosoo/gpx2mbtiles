# 设计：瓦片代理与缓存

## 为什么代理只覆盖 Windy

OTM 与 OSM 浏览器可直连，走代理只会白白消耗服务器带宽。
因此代理层用白名单 `TILE_PROXY_LAYERS` 控制，默认只含 `windy`。

## 缓存放在哪

`<data_dir>/tilecache/<layer>/<z>/<x//1000>/<x>/<y>.tile`

按 x 分片（每 1000 一个目录）避免单目录文件过多。

与任务成品（`<data_dir>/tasks/...`）分开存放，因为两者生命周期完全不同：
- 瓦片缓存是**只读缓存**，丢了自动回源，可随时淘汰
- 成品是**交付物**，过期才删

## 淘汰策略

- 超上限时按 `mtime` 从旧到新删除，删到上限的 85%
- 每次读取会 `utime` 更新访问时间，所以 mtime 实际是"最后访问时间"
- 淘汰后清理空目录

## 磁盘保护

- `TILE_CACHE_MAX_BYTES` 默认 8GB
- `DISK_MIN_FREE_BYTES` 默认 3GB：低于此值停止写入缓存，
  但**继续提供读取**，已有缓存不受影响

## 浏览器缓存

关键在于响应头：

```
Cache-Control: public, max-age=2592000, immutable
ETag: "<layer>-<z>-<x>-<y>-<sha1 前 20 位>"
```

- `immutable`：让浏览器对同一 URL 完全不走网络，连 304 都不发
- ETag 用**内容哈希**而非 mtime：mtime 会随回源时间变化，
  导致同一瓦片 ETag 漂移、浏览器缓存无谓失效

实测：同一 z 来回平移 6 轮，被重复请求的瓦片为 0。

## 并发与限速的分层

| 链路 | 是否限速 | 由谁控制 |
|---|---|---|
| 浏览器 → 服务器 | 否 | 浏览器自身并发 |
| 服务器 → 上游 | 是 | 服务端 `TileFetcher`（并发 + 间隔 + 退避） |

前端只保留失败重试（服务端偶发 502/503 时退避重取），不干预加载节奏。

## 与既有 TileFetcher 的复用

代理直接复用 `app/tile_downloader.py` 的 `TileFetcher`，
沿用 `.env` 里的 UA / Referer / 代理配置，避免两套实现漂移。
按图层临时切换 `settings` 中的模板与请求头，用完即恢复。
