# Proposal · KML 转 GPX 转换服务

## Why

两步路等 App 导出的 KML 里，「标注点」的 `<Placemark>` 没有 `<name>`，
轨迹片段的名称只有 `轨迹片段1` 这种默认值，凭据全在 `<ExtendedData>` 与
`<description>` 的富文本/图片附件里。这些文件被 GPSBabel 之类工具转成 GPX 时，
工具只做坐标搬运、不整理命名，于是导入到只认 GPX 的 App 后：

- 33 个航点全部无名，列表里只剩「海拔」一行；
- 轨迹名丢失，回退成日期时间（截图里 6 条记录全是「2026年10月17日 16:57」）；
- 图片附件的只有 id，看不出是哪张照片。

结果就是导入的数据没法看、没法找。需要一个服务，在转换时把名称重新组织出来。

## What Changes

- **新增转换能力**：上传 KML/KMZ 或粘贴文本，得到一份保留了时间、海拔、
  心跳与扩展字段的 GPX 1.1；响应同时返回转换摘要（轨迹数、航点数、命名统计）。
- **航点自动命名**：按文件厂商（目前覆盖两步路 2bulu）识别「标注点」，
  依据多级来源依次尝试 `<name>` → 用户备注 → 照片文件名 → **位置名称**，
  并在名称里带上航点序号，撞名时自动加后缀 —— 保证「每个航点都有不重名的名字」。
- **航点位置换算**：把每个航点定位到轨迹上，算出「已走里程」与「累计耗时」，
  名称形如 `#07 3.08km · 1:28`，比抬头看时钟更能反映当时走到哪了。
- **轨迹自动重命名**：默认「地点 + 日期 + 轨迹类型」，**地点在最前**（如
  `英德雪山嶂环线 2023-02-18 爬山`），支持用户在页面填写自定义轨迹名覆盖。
- **附带统计**：为每个航点和整条轨迹计算累计里程、距离起点的耗时，
  写进 `<desc>`，让只显示 desc 的 App 也能看出进度。
- **新增页面**：`web/convert.html`（手机可用），拖拽/选择文件 → 预览命名 → 下载 GPX；
  生成器页与回放页加入口。
- **纯服务端解析**：转换在服务端完成，前端只做表单与预览，不依赖浏览器特性。

## Capabilities

### New Capabilities

- `track-conversion`：把 KML / KMZ 转换为标准 GPX，并对轨迹与航点做可解释的重命名。

### Modified Capabilities

- `offline-map-generation`：上传入口接受 .kml / .kmz，需要与现有 GPX 解析共用同一套点提取逻辑。

## Impact

- 新增：`app/kml_processor.py`（KML/KMZ 解析 + 命名规则）、`app/gpx_writer.py`（GPX 1.1 输出）、
  `POST /api/convert`、`web/convert.html`、测试用例与样例文件。
- 修改：`app/main.py`（路由 + 上传类型）、`app/gpx_processor.py`（点提取抽出复用）、
  `web/index.html`、`web/player.html`（入口链接）、`web/portal.html`、`README.md`。
- 依赖：无新增。KMZ 用标准库 `zipfile`；解析用标准库 `xml.etree`。
- 兼容性：非破坏性。现有 GPX 生成与回放流程不变；`/api/convert` 只读、不落盘、不建任务。
- 合规：与瓦片源无关，不触发任何外部请求。
