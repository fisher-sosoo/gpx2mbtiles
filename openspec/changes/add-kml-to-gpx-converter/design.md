# Design

## Context

对照本项目的真实样本（两步路导出的 `英德雪山嶂环线` KML + 由它做的 GPX）：

| 事实 | 数值 |
|---|---|
| Document 的 `<name>` | `2023-02-18 英德雪山嶂环线`（含日期与地点） |
| 轨迹 `<gx:Track>` | 1 段，1052 个 `<gx:coord>` / `<when>`，位于 `Folder「轨迹」` 下的 `Placemark`，名 `轨迹片段1` |
| 点 `<Placemark>` | 32 个：`startPoint`/`endPoint` 各 1（有 `<name>`），`realPoint` 30 个（无 `<name>`） |
| 航点信息位置 | `<ExtendedData>` 的 `Latitude/Longtitude/Altitude/Time(epoch ms)/FileId/attach` + `<description>` 里的 HTML（经度/纬度/海拔/本条记录的挂载时间） |
| 现有 GPX 的丢失方式 | 30 个 `<wpt>` 无名；`<trk>` 无 `<name>`；GPSBabel 把文案塞进 `<extensions>`，多数 App 不读 |

约束：

- 现网是 2C/1.8G 单机，转换必须轻量，不引入新依赖（标准库即可）。
- 前端无构建步骤，页面只能写原生 JS。
- 部署走 git + CI，Caddy 只反代 `/gpx/*` 与 `/api/*`，新增页面必须放在这两个前缀下。

## Goals / Non-Goals

**Goals:**

- 一次转换把 33 个点位变成「每个都有可读、可区分名称」的 GPX。
- 命名规则对厂商文件做适配，但对非两步路文件也能退化到通用规则。
- 转换是可解释的：摘要能说明每个名字是哪一级来源给的，用户能判断是否要改。

**Non-Goals:**

- 不追求无损往返 KML（样式、图标、图片二进制不搬运）。
- 不做多厂商插件化架构：先做「通用规则 + 一步已知厂商适配」，避免过度设计。
- 不做浏览器端转换（回放页已有 KML 预览，转换走服务端更一致、可测试）。

## Decisions

### D1 · 转换放在服务端，接口无状态

`POST /api/convert` 接收 multipart（`file` 或 `text`）+ `track_name` 可选参数，
直接返回 JSON：`{gpx, filename, summary}`。

- 不做任务、不落盘：输入 < 10MB、解析毫秒级，落盘只会引入清理负担。
- 返回 gpx 文本而不是文件流，让页面可以先展示摘要再让用户决定下载（下载用 Blob）。
- 复用现有 `AUTH_TOKEN` 依赖：与其它 `/api/*` 一致；未配置 token 时放行。

替代方案：另建一个独立服务 —— 否决，单机部署没有必要，且门户反代要多一条规则。

### D2 · 解析与命名分两层，命名可单测

- `app/kml_processor.py`：KML 元素树 → 中间结构 `KmlPoint` / `KmlTrack`（纯数据）。
- 命名规则是中间结构上的纯函数：输入点与上下文，输出名称与来源标记。
- `app/gpx_writer.py`：中间结构 → GPX 文本。

这样「坐标搬对了但名字还是错」和「名字对了但坐标丢了」两类问题可以分开测。

### D3 · 航点命名：四级来源，位置名称用「已走里程 + 累计耗时」

依赖链（每个 realPoint 依次尝试，取第一个非空）：

1. `<name>` —— 用户手动在 App 里命名的点（样本里没有，但真实数据会有）。
2. 用户备注 —— 两步路 `ExtendedData > Data name="description"` 或 `<description>` 里除固定四行（经度/纬度/海拔/时间）之外的文字。样本全空 → 落到下一级。
3. 附件文件名 —— `FileName` 或 `attach` JSON 里的 `fileId` 派生的 `照片 1201359289`。
4. 位置名称 —— `已走里程 + 累计耗时`。

**位置名称怎么算**（关键细节）：

- 样本里 30 个 `realPoint` 与轨迹顶点**逐点重合**（坐标完全相同），并且沿轨迹严格单调前进。
  所以「沿轨迹已走里程」就是该顶点的累计里程：第 1 个点 0.38 km，第 30 个点 8.85 km，
  全程 11.23 km。
- 累计里程按 `gx:coord` 相邻点 Haversine 累加；对不重合的航点取轨迹上最近位置并按到该位置的插值算。
  定位用 KDTree，不用 O(n·m) 全量比较（回放页里上千个点会卡）。
- 累计耗时 = 航点时间 − 轨迹首点时间，取整到分钟。航点时间本身仍有坑：
  `ExtendedData.Time` 比 `<description>` 里的「时间」早 487 秒（前者是该记录挂载到轨迹的时刻），
  所以**优先用 description 解析出的时间**，解析不到才回退 `ExtendedData.Time`。
  两者都晚于轨迹起点，差值为正。
- 无时间可用（KML 没写 `<when>`）时退化为 `里程 + 海拔`。
- 名称里的时间因此是「走了多久」而不是「几点」，与时钟无关，也就不需要时区配置。

输出形态：`#07 3.08km · 1:28`（序号补两位 + 里程两位小数 + 累计耗时 h:mm）。
来源为 1/2/3 时同样带序号。重名时追加 `(2)`、`(3)`。
起终点单独命名 `起点` / `终点`，不占序号。

**序号与重复点**：样本第 7/8、21/22 个点坐标完全相同（各停留十几秒），
两条的里程都是 3.08 km / 6.21 km，靠序号与分钟差（`1:28` 与 `1:29`）区分——
这是真实停留，不是转换错误。

替代方案：

- 用 `FileId` 当名称 —— 否决，App 里看到一串数字等于没命名。
- 用本地时刻（`13:35`）—— 否决，用户明确要求按「累计耗时 + 已走距离」，比钟点更能反映进度。

### D4 · 轨迹命名：地点优先，日期在后

样本 Document `<name>` = `2023-02-18 英德雪山嶂环线`，
拆开就是「日期 + 地点」，运动类型在 `SportTypeName`=爬山。

**地点在最前**：App 的轨迹列表按名称排序/浏览，地点是用户找东西时最先扫的信息，
日期放前面会把 30 条轨迹都挤成同前缀，反而更难找。

规则：

1. 从「文件名 / Document 名 / 轨迹名」里剥掉日期前缀与 `轨迹片段N` 占位词，剩下的作为**地点**候选。
2. 有用户指定 → `<用户名称>`（多段时 `<用户名称> 1/2`）。
3. 否则 `<地点> <日期> <运动类型>` → 样本为 `英德雪山嶂环线 2023-02-18 爬山`，
   缺项省略；无地名时退化为 `<日期> <运动类型>`。
4. 隐藏项：占位词（轨迹片段、Track、Untitled、KML）绝不进入最终名称。

替代方案：用起终点地名（`横坑`）→ 作为兜底保留，但优先文件地名（`英德雪山嶂环线` 信息量更大）。

### D5 · 里程/耗时写进 desc，不写非标准元素

每点的 `<desc>` 追加一行 `已走 3.42 km · 累计 1h12m`（与位置名称同源，避免两处数字打架）。
坐标和海拔用标准元素，其余（运动类型、总里程、爬升、原名称）放 `<extensions>`：
标准元素保证任何 App 都能读，扩展字段留给愿意读的工具。

### D6 · KMZ 用标准库 zipfile；编码先嗅探再兜底

KMZ 就是 ZIP，`zipfile` 足够，无需第三方。KML 编码按 UTF-8 解码，
失败回退 GB18030（国内工具偶有 GBK 导出），再失败才报错。

### D7 · 生成器页顺带支持 KML

`/api/submit` 与 `/api/estimate` 现在只收 .gpx/.xml。扩展名白名单增加 `.kml/.kmz`，
内部把「取点」统一到同一函数：上传是 KML 时先转换再取点。
这样用户下载完转换后的 GPX，也可以直接把原 KML 丢进生成器。

### D8 · AI 辅助命名：只在显式开启时调用，失败一律回退

规则名称（`#07 3.07km · 1:08`）解决了「名字缺失」，但没有解决「不知道走到哪了」。
模型能从海拔剖面读出地形与节奏，正好补上这一层。

决策：

- **可选而非默认**：`/api/convert` 增加 `ai_names` 参数，默认关闭。
  开关放页面复选框，用户勾了才发外部请求。
- **输入是结构化摘要，不是原始点云**：只发「序号 / 累计里程 / 累计耗时 / 海拔 /
  两点间升降」加一句轨迹总览（全程、爬升、起点与最高点海拔、环线或穿越）。
  实测 30 个航点约 770 prompt tokens，一次调用 ~2 秒。
- **输出只当候选名**：解析 JSON 数组，逐条校验序号能对上、名称非空且长度合理；
  任何一条不合格就丢弃该条，该航点回退到规则命名。整体失败也不影响转换。
- **人工名称永远优先**：文件里已有 `<name>` 或用户备注的航点不参与 AI 覆盖。
- **来源标记新增 `ai`**：摘要 `name_sources` 如实统计，页面提示「AI 推测，仅供参考」。
- **密钥只走环境变量**：`AI_API_KEY`（或本机未入库的 `apikey` 文件），
  默认读不到就跳过；`.gitignore` 已加 `apikey`。请求超时与并发都要有上限，
  避免一次转换卡住 worker。

替代方案：

- 把 AI 当默认：否决 —— 每次转换都产生外部请求与费用，且离线时体验变差。
- 让模型直接改轨迹名：否决 —— 轨迹名是「地点+日期+类型」的结构化信息，
  模型没有额外依据，反而容易臆造。

## Risks / Trade-offs

- **[厂商私有字段无文档]** → 解析只依赖我在样本里核对过的字段名，全部做「有则用、无则跳过」，
  遇到未识别结构不致失败；同时用样本文件写回归测试锁住行为。
- **[里程依赖轨迹本身的数据质量]** → 若轨迹点稀疏或跳变，里程会偏短。
  用样本校验：Haversine 累计 11.23 km，两步路自报 11.61 km（差 3%，属抽样误差）；
  摘要里同时给出「文件自报里程」与「算出里程」，不一致时页面提示用户核对。
- **[定位计算的开销]** → 上千航点 × 上千轨迹点的定位必须走 KDTree，
  不做 O(n·m) 全量比较；回归测试里放一个大点数的用例。
- **[AI 可能编造地名]** → 提示词禁止输出真实地名，只允许描述地形与动作；
  页面对 AI 来源显示「推测」字样。用户仍可在 App 里自行改名。
- **[AI 调用拖慢转换]** → 设超时（默认 30 秒）与「仅在有航点时调用」；
  失败即回退，不让转换返回错误。
- **[密钥泄露]** → 只从环境变量/未入库文件读取，绝不写进响应或日志；
  `apikey` 已加入 `.gitignore`，CI 用仓库 Secret 注入。
- **[重名、重复点位让「33 个点」看起来对不上]** → 摘要里明确列出「按来源统计的命名数量」，
  页面直接展示，避免用户以为丢了点。
- **[扫描版 KML 结构五花八门]** → 解析器只认 `Placemark/Point/LineString/gx:Track`，
  其它（GroundOverlay、多几何体的 Polygon）忽略并在摘要里给出「已跳过 N 个要素」的提示。
