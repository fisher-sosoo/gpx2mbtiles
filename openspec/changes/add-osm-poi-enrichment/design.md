# Design

## Context

实测（docs/NEXT-ITERATIONS.md 第 4 节）：Overpass 单次查询 **41.8 秒**，
只有 `overpass-api.de` 可用（kumi / private.coffee / mail.ru 全 5xx），
墙内直连 DNS 失败必须走代理。数据质量极好：垭口离轨迹 1~11 米。

## Goals / Non-Goals

**Goals:**

- 把 OSM 里「有名字的地物」变成航点，且不刷屏。
- 查询慢但不能卡住用户。

**Non-Goals:**

- 不做瓦片级地图匹配，只按几何距离与相交判断。
- 不缓存原始 Overpass 响应（体积大），只缓存筛选后的结果。

## Decisions

### D1 · 异步任务 + 结果落项目

`POST /api/projects/{id}/pois` 立即返回 `started`，后台线程跑查询写 `pois.json`；
前端 3 秒轮询。再次打开项目直接读缓存，不重查。

**替代方案**：同步接口 —— 否决，40 秒的请求必然超时。

### D2 · 距离阈值按类型分

| 类型 | 阈值 | 依据 |
|---|---|---|
| 垭口/营地/山屋/避难所 | 200m | 实测 1~32m，卡死 200m 安全 |
| 山峰 | 3000m | 三神山离轨迹 1.7~2.3km，全程可见，该标 |
| 湖泊 | 300m | 牛奶海 150m、五色海 228m |
| 村镇 | 仅起终点 200m 内 | 路过村镇不标，避免建筑刷屏 |
| 河流 | 几何相交 | 按距离会把沿河段标上百次 |

一刀切 200m 会把三神山全滤掉；一刀切 3km 会把垃圾全收进来。必须分类。

### D3 · 过河用线段相交，且处理退化

实测轨迹穿过河流时，交点常常**正好落在轨迹顶点或河段端点**上，
只判严格「一正一负」会漏判。实现里额外处理 `|orient|≈0 且落在包围盒内` 的接触情形。

河流段用网格索引，避免 24768 个轨迹点 × 几百条河段的暴力比较。

### D4 · 同名去重保留最近

同一条河、同一座山可能有多个 OSM 要素。按 `(name, kind)` 去重，保留离轨迹最近的。

### D5 · 结果并入 GPX 但不改原轨迹

导出时把地名点作为额外 `<wpt>` 插到 `</gpx>` 前，轨迹点一个不动。
下载用 `/export`，普通 `/download` 仍是纯轨迹。

## Risks / Trade-offs

- **[公共设施滥用]** → 带 UA、有超时、结果落盘不重复查；`POI_ENABLED=0` 可整体关闭。
- **[英文名混入]** → 优先 `name:zh`，没有才退 `name`；实测个别要素只有英文名（Dolma La）。
- **[包围盒过大导致查询慢]** → 外扩默认 500m，可调；超大轨迹需注意。
