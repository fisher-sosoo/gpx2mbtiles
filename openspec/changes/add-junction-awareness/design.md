# Design

## Context

方向 #8。核心问题是「怎么知道这里有没有岔路」。
调研见 proposal.md：IMG 有拓扑但无工具解析；在线只查 highway 只要 30~38 秒。

## Goals / Non-Goals

**Goals:**

- 用真实路网判定岔路，把转向分成「路口转向」与「地形转向」。
- 查询失败时优雅降级，不拖累现有功能。

**Non-Goals:**

- 不解析 Garmin IMG（见下）。
- 不做路径规划或导航。

## Decisions

### D1 · 先不解析 otm-china.img

调研结论：文件是标准 DSKIMG，每个瓦片都带 NET/NOD（路由拓扑），**数据是够的**。
但两台机器上都没有 GDAL、Java/mkgmap、osmium 等任何可用工具，
且格式是比特打包 + compact-6 字符串，自写解析器是独立的大工程；
4.2 GB 文件还要搬进 1.8 GB 内存的服务器。

实测替代方案只要 30~38 秒、185 KB，因此本轮先用在线路网。
IMG 解析记为后续独立方向。

### D2 · 路口 = 附近有两条以上不同道路

不需要理解路网拓扑：把每条 way 的顶点收进来，对轨迹上每个点统计
**25 米内出现的不同 way 数**，≥2 即为路口。这不需要解析 turn restriction，
也不需要连通性，实现简单且对判定「有没有岔路」足够。

### D3 · 相邻采样点合并

原型里 51 个点合并成 6 处（索引差 ≤8 视为同一路口）。
不合并会得到一串同一路口的重复提示。

### D4 · 转向按「离最近路口多远」分类

路口附近（沿用同一 25 米阈值）的显著转向 = 路口转向；
其余 = 地形转向。地形转向仍保留，但提示时降权。

### D5 · 与地名查询解耦

两者 bbox 相同但请求不同（一个只取节点、一个只取线几何），
缓存在一起会让失效互相牵连，所以分开存、分开失败。


### D6 · 离线路径：自写流式解析器，不装重依赖

用户已确认 IMG 内容最终会放到服务器，且允许安装依赖。但权衡后仍选择纯 Python：

| 方案 | 镜像增量 | 风险 |
|---|---|---|
| GDAL | ~400 MB，且无 Garmin IMG 驱动 | 无收益 |
| Java + mkgmap | ~200 MB | mkgmap 写 IMG，不读 IMG |
| **纯 Python 流式解析** | **0** | 需自行实现，但格式有公开规范 |

关键是内存：单体 4.3 GB，但解析器永远只 `seek` 到目标瓦片读其子文件，
峰值与文件大小无关。

### D7 · 拆分与单体共用一套解析

数据是按长度累加的连续布局，所以「按累计偏移切出单瓦片 .img」是平凡操作。
解析器接受任意 IMG 文件，单体与拆分件都能读，不必维护两套逻辑。

### D8 · 岔路优先取自 NOD 的节点度数

若走离线路径，NOD 里每个路由节点都记录了它连接的道路。
**节点的道路度数 ≥ 3 即路口** —— 这比几何相交判定更准，
因为它天然排除了「两条平行路靠得近但不相交」的误判（见 Risks）。

## Risks / Trade-offs

- **[路网密集的景区会误判]** → 村镇里建筑之间也有小路，可能到处是「路口」。
  缓解：只统计道路类 tag，且路口提示按里程去重并限量。
- **[多一次 30~40 秒的查询]** → 异步执行，不阻塞转换与地名补点。
- **[两条平行但不相交的路]** → 顶点距离近也会被判为路口。这是已知局限；
  25 米阈值下影响有限，若误判明显再引入连通性判断。

## Open Questions

- 是否需要把岔路口也写进导出的 GPX（作为独立航点）？
  倾向先只用于命名与分析，避免航点数量膨胀。
