# Proposal · 岔路感知：用路网判断转向是不是「真路口」

## Why

方向 #8 的目标：让转向提示知道「这里到底有没有岔路」。
现在的转向完全由几何推出，分不清**绕过一块石头的左右横移**和**在路口选左还是选右**。

用户提供了本地 Garmin OTM 地图（`otm-china.img`，4.2 GB），希望尽量不依赖在线地图。

## 调研结论（实测）

### 1. `otm-china.img` 确实是标准 Garmin DSKIMG

- 头部 `DSKIMG` + `GARMIN`，地图名 `OpenTopoMap China`，日期 26-05-26。
- 由多个瓦片组成，**每片都带 RGN / TRE / LBL / NET / NOD**（部分带 DEM）。

| 瓦片 | RGN | TRE | LBL | NET | NOD |
|---|---|---|---|---|---|
| 53100228 | 4.48 MB | 0.06 MB | 0.29 MB | 0.24 MB | 0.60 MB |
| 53100287 | 5.46 MB | 0.07 MB | 0.19 MB | 0.93 MB | 2.26 MB |

**NET + NOD 就是路由拓扑**，所以「离线判定岔路」在数据上是成立的。

### 2. 但没有现成工具能解析

| 工具 | 本地 | 服务器 |
|---|---|---|
| GDAL / ogrinfo | 无 | 无 |
| Java / mkgmap | 无 | 无 |
| osmium / gpsbabel | 无 | 无 |

IMG 是比特打包 + compact-6 字符串的私有格式，自写解析器工作量与风险都很大，
而且要把 4.2 GB 文件搬到 1.8 GB 内存的服务器上才有用。

### 3. 在线只查 highway 反而很便宜

| 查询 | 耗时 | 响应 |
|---|---|---|
| 现有地名查询（节点） | 65~74 s | 小 |
| **只查 highway（含几何）** | **30.8~38.6 s** | **185 KB** |

### 4. 岔路原型跑通了，而且和转向点吻合

在英德样本上：12 条路 → 合并出 6 个岔路点。

| 岔路点 | 位置 | 交汇路数 | 对应已有转向 |
|---|---|---|---|
| pt#139 | 24.36346,113.63365 | 2 | km≈1.5 → 转向 #02 (1.62 km) |
| pt#574 | 24.38058,113.61652 | 3 | km≈6.1 |
| pt#706 | 24.38164,113.62679 | 3 | km≈7.5 → 转向 #26 (7.56 km) |
| pt#8 / pt#1051 | 起终点 | 3 | 登山口/停车场多路交汇 |

**转向点与岔路点对得上**，说明这条路可行。


## 补充调研（用户要求内容最终上服务器、允许安装依赖）

### 5. 单体 IMG 的结构已解析清楚

| 项目 | 实测值 |
|---|---|
| 子文件头数量 | **1213** |
| 头区（0x0 ~ 0x97E00） | **622080 字节** |
| 数据起始 | 0x97E00 |
| 子文件长度合计 | 4231 MB（文件 4301 MB） |
| 每瓦片构成 | RGN / TRE / LBL / NET / NOD（部分 DEM） |

规律：**第一个"子文件"就是头区本身**（长度恰好 622080），
之后每个子文件的数据按长度**累加**定位。这意味着可以用
`seek()` 直接跳到任意瓦片的任意子文件，**不必把 4.3 GB 读进内存**。

### 6. 内存策略

- 解析单个瓦片只需读该瓦片的 TRE（几十 KB）+ NOD/NET（几百 KB ~ 几 MB）。
- 全程 `seek` + 分段读，峰值内存目标是 **< 50 MB**，与文件大小无关。
- 纯 Python 实现，**不依赖 GDAL / Java / mkgmap**，不增加镜像体积。

### 7. 关于"拆成多个文件的 gmap"

- 本机未找到 BaseCamp 那种按瓦片拆分的安装目录（只有 `gmaptz.img` 0.57 MB 可作测试样本）。
- 但既然数据是连续拼接的，**拆分是平凡的**：按累计偏移把每个瓦片写成一个独立 `.img`，
  解析逻辑与读单体完全一致。因此两条路可以共用同一个解析器。
- 也可支持"只把用到的瓦片推上服务器"，进一步省磁盘。

### 8. 可分阶段

- **阶段 A（先做，已具备条件）**：在线只查 highway 判岔路。实测 30~38 秒、185 KB。
- **阶段 B**：纯 Python 解析本地 IMG 的 NOD/RGN，彻底离线。
- 两阶段共用同一套"岔路 → 转向分类"逻辑，只是数据来源不同。

## What Changes

- **新增岔路查询**：只取 `highway` 路网几何，独立于地名查询，可缓存、可降级。
- **岔路识别**：轨迹附近同时出现两条以上不同道路的顶点 → 判定为岔路口，按里程合并。
- **转向升级为路口转向**：转向点若落在岔路附近，标注为「岔路口」并给出可选方向数；
  不在岔路附近的转向降级为地形绕行，不再作为主要提示。
- **地图与图例**：岔路点在页面上单独样式标出（与地形转向区分）。
- **失败即降级**：岔路查询失败时，行为退回当前版本（纯几何转向），不影响其它功能。

## Capabilities

### New Capabilities

- `junction-awareness`：基于路网判定轨迹上的岔路口，并用于转向提示。

### Modified Capabilities

- `track-conversion`：转向描述区分「路口转向」与「地形转向」。

## Impact

- 新增：路口查询与判定模块、接口字段、页面图层。
- 修改：转向提示逻辑、地图绘制、测试。
- 依赖：无新增（复用现有 HTTP 客户端与代理）。
- **不在本轮**：解析 `otm-china.img`。调研已确认数据可用但缺工具，
  自写解析器远大于一轮的工作量，先不做。
