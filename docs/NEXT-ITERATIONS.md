# 后续迭代方向 · 可行性评估

> 评估时间：2026-10 ｜ 基线版本：v1.4.1
> 验证对象：`2026-10 洛亚大转-波拥措前下撤.gpx`（6 段 / 24768 点 / 49.5km / 海拔 2975–4766m，稻城亚丁）

本文只记录**实测结论**与**技术约束**，每节都附上验证方式。凡写「已验证」的，
都是在服务器容器里真实跑过的，不是纸面推断。

---

## 1. AI 按转向标注左右拐

**结论：可行，已验证。** 成本最低，建议作为第一个增量。

### 实测

在真实轨迹上做转向识别（90m 弦长算航向、50m 采样、50° 阈值、250m 内合并）：

| 指标 | 结果 |
|---|---|
| 识别出的转向点 | 42 个 |
| 左拐 / 右拐 | 19 / 23 |
| 密度 | 平均 1 个 / 1.18 km |
| 最大转向 | 160°（发卡弯，符合山区路线特征） |

样例输出：

    km     方向    转角    海拔
    0.15   左     68°    3091m
    2.05   右     84°    3208m
    3.29   右    153°    3173m    ← 发卡弯
    11.18  左    149°    3475m

### 做法

现在 AI 只拿到「里程/耗时/海拔/升降」，缺方向感。补三类几何量即可：

- **转角与方向**：`+84°右` / `-68°左`，直接进提示词
- **弯后 200m 的地形**：转弯后是继续爬升还是转平，决定是「右转切上山脊」还是「右转下沟」
- **转弯密度**：连续多个急弯 = 之字形爬升（`Z 字形盘山`），模型能识别出来

### 风险

GPS 抖动会造成假转向。已有缓解手段：弦长航向 + 持续性校验 + 距离合并，
阈值都是纯参数，可按实际数据再调。**不需要任何新数据源，纯几何计算。**

## 2. 历史转换管理（项目空间）

**结论：可行，工程量大但无技术风险。**

现在是「无状态转换」：`/api/convert` 不落盘，刷新即丢。要做的是：

- 每次转换生成一个 **project**（目录 + 元数据）
- 保存输入原件、输出 GPX、摘要 JSON、AI 结果，后续可重新进入
- 支持：历史列表、重新打开、带新参数重转、删除

### 存储选型建议

直接复用现有 `task_manager` 的模式（SQLite 账本 + 目录），而不是另起一套：

    data/projects/<project_id>/
        input.kml          原件（重转用）
        output.gpx         产物
        summary.json       摘要（含命名来源、里程、耗时）
        ai.json            AI 原始返回（便于回溯）
        meta.json          参数、时间、状态

**不选**纯文件系统扫描：历史条目需要筛选/排序/分页，扫目录会随文件数线性变慢；
SQLite 已有现成实现，加一张表比造轮子便宜。

### 注意

- 磁盘配额：现在 `data/` 有瓦片缓存（上限 8GB），项目空间要单独设上限与过期策略
- 与瓦片任务的关系：一个 project 可以关联 0..N 个地图生成任务，别混成一张表

## 3. 多轮对话修正

**结论：可行，但是**架构级变更**，建议放在 2 之后做。**

要在页面里做「专做 GPX 航点补充的对话式助手」，需要：

| 能力 | 现状 | 缺口 |
|---|---|---|
| 会话与消息存储 | 无 | 新增表 + 接口 |
| 多轮上下文 | 单次调用 | 需要把历史消息与轨迹摘要一起喂 |
| 异步任务 | 有（task_manager） | 可复用其模式 |
| 流式输出 | 无 | SSE 或轮询，二选一 |

### 关键设计问题

**上下文怎么控制**：一条轨迹有上万个点，不可能每轮都全量塞给模型。
必须先把轨迹压成**结构化摘要**（分段、转向点、POI、海拔剖面），
对话只在摘要上叠加用户的修正意见。这也正好复用了方向 1 和 4 的产物。

**修正结果怎么落地**：用户说「第 7 个点改成垭口」，要能定向改单个航点，
而不是整体重生成。所以命名结果需要稳定的 `seq` 主键（已经是了）。

### 折中方案

先做「单轮重试 + 可编辑」：用户能改某个航点的名字并保存，
不满意就整体换个提示词重跑。这能覆盖 80% 的修正需求，
成本只有完整对话系统的 1/3。等真觉得不够，再上多轮。

## 4. 叠加 OpenTopoMap 补充地名航点

**结论：可行，数据质量超出预期，但有性能约束。**

### 实测：OSM 数据是这个路线最有价值的部分

对轨迹包围盒查询 Overpass，120 个要素里 **67 个有名字**：

| 类型 | 数量 | 实例 |
|---|---|---|
| 垭口 saddle | 12 | 黑湖垭口 4720m、松多垭口、杂巴拉垭口 4750m、蛇湖垭口 4685m |
| 牛场/营地 camp_site | 18 | 万花池牛场、新果牛场 4270m、嘎洛牛场、波拥措营地 |
| 山峰 peak | 16 | **仙乃日 5998m、央迈勇 6033m、夏诺多吉 5951m** |
| 湖泊 water | 38 | 五色海 4700m、牛奶海 4600m、勒西措、珍珠海 |
| 村镇 place | 14 | 亚丁村、呷洛、扎灌崩、龙同坝 |

### 实测：POI 与轨迹的贴合度

| POI | 类型 | 到轨迹最近距离 | 建议 |
|---|---|---|---|
| 杂巴拉垭口 | 垭口 | **1m** | 标注 |
| 黑湖垭口 | 垭口 | **3m** | 标注 |
| 松多垭口 | 垭口 | **7m** | 标注 |
| 蛇湖垭口 | 垭口 | **9m** | 标注 |
| 万花池牛场 | 牛场 | 19m | 标注 |
| 新果牛场 | 牛场 | 32m | 标注 |
| 扎灌崩 | 村 | 7m | 标注（终点） |
| 牛奶海 | 湖 | 159m | 标注 |
| 仙乃日 / 央迈勇 / 夏诺多吉 | 山峰 | **1681–2272m** | 标注（地标） |
| 亚丁村 | 村 | 2985m | 跳过 |

### 由此得出的三条规则（和你的要求对上了）

1. **距离阈值要按类型分**，不能一刀切：
   - 垭口 / 牛场 / 营地 / 过河点：**必须 < 200m**（实测都在 40m 内）
   - 著名山峰：**放宽到 3km**（三神山离路线 1.7–2.3km，但全程可见，是该标的）
   - 村镇：**只在起终点标**，路线穿村而过时不标
2. **河流只在过河时标**：不能按距离判定，要做**几何相交**（轨迹线段 ∩ 河流线）。
   沿河走几十公里只标 1~2 次过河点，而不是每公里一次。
3. **同类去重**：同一座山峰/同一条河，全程只标一次（按 name 去重，取最近点）。

### 性能约束（这是真正要解决的）

| 问题 | 实测 |
|---|---|
| Overpass 查询耗时 | **41.8 秒**（包围盒很小也这么慢） |
| 可用镜像 | 只有 `overpass-api.de` 通；kumi / private.coffee / mail.ru 全部 5xx |
| 直连 | DNS 解析失败（墙内），**必须走代理** |

结论：**不能同步调用**。必须做成后台任务 + 结果缓存（同一区域查询结果可复用），
前端轮询。否则用户点一下要等 45 秒，体验很差。

### 合规

Overpass 是公共设施，必须：加 `User-Agent`、限流、结果落盘缓存、不重复查询。
和瓦片源一样属于「个人自用、不得滥用」的红线范围。

## 5. 出图 + 行前指南 + 天气

**结论：天气已验证可用；出图需要抉择方案；文字指南是最容易出价值的。**

### 天气：已验证

Open-Meteo（免费、无需 key）：

| 项 | 结果 |
|---|---|
| 响应时间 | **2.6 秒** |
| 数据 | 7 天逐日：温度/降水/降水概率/天气码/风速 |
| 海拔修正 | 支持 `elevation=4500` 参数，按实际海拔给温度 |

实测输出（稻城亚丁）：

    2026-10-17  -8.6~2.3°C  rain=0.0mm  p=0%   code=1  wind=19km/h
    2026-10-21  -7.1~2.4°C  rain=0.0mm  p=25%  code=0  wind=23km/h

> 注意：不带 `elevation` 时用的是网格默认海拔，带 `elevation=4500` 数值会变，
> 两者哪个更准需要在实现时用真实观测校对，不能直接采信。

### 出图：两种方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 服务端渲染 | Pillow 画线 + 拼瓦片 | 可批量/可定时 | **镜像里没装 Pillow**，要加依赖；瓦片拼接自己实现 |
| B 前端渲染 | 复用 `player.html` 的 canvas | 已有成熟代码，零新依赖 | 只能在浏览器里出图，不能后台批量 |

**建议先做 B**：回放页已经能导出带图例的 PNG，把它扩展成「行前指南模板」比重新写一套便宜得多。

### 文字指南：最容易出效果

把已有的东西串起来就是指南，不需要新技术：

    轨迹概况：49.5km / 爬升 3722m / 海拔 2975–4766m / 6 段
    关键节点：黑湖垭口 4720m（km 12）→ 杂巴拉垭口 4750m（km 24）→ 波拥措营地（km 41）
    天气窗口：10-18 ~ 10-20 连续晴，10-21 起降水概率 25%
    风险提示：高海拔垭口 4700m+，10 月夜间 -8°C，需防失温

模型把「轨迹几何 + POI + 天气」三者结合，正是能说出人容易忽略的细节的地方。

## 建议的推进顺序

| 序 | 方向 | 依赖 | 预估 | 理由 |
|---|---|---|---|---|
| 1 | **转向感知命名** | 无 | 小 | 纯几何，立刻能用，验证「AI 输入结构化摘要」这条路 |
| 2 | **项目空间/历史** | 无 | 中 | 后续所有功能的载体；越早做越省事 |
| 3 | **OSM POI 补充** | 需要 2 存产物 | 中大 | 数据已验证；难点是 45s 查询要做成异步 |
| 4 | **行前指南（文字+天气）** | 需要 1、3 | 中 | weather 已验证；文字比出图性价比高 |
| 5 | **出图 PNG** | 需要 3、4 | 中 | 用前端 canvas 方案，避免加 Pillow |
| 6 | **多轮对话** | 需要 1–4 的产物 | 大 | 架构级；先用「可编辑+重跑」过渡 |

## 总体判断

五个方向**全部可行**，没有卡死的。真正需要设计决策的只有三处：

1. **Overpass 45 秒** → 必须异步 + 缓存，不能同步接口
2. **出图方案** → 建议前端 canvas，避免给镜像加 Pillow
3. **多轮对话** → 建议先做单轮可编辑，别一上来就做完整 chat

其余都是增量实现，可以按上表逐个交付。
